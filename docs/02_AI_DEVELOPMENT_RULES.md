# AI Development Rules

Version: 1.0

Status: Approved

Owner: Alexandre Silva

Technical Lead: ChatGPT

---

# Purpose

This document defines the permanent rules that every AI assistant must follow while contributing to Project Atlas.

These rules override implementation preferences whenever applicable.

---

# Rule 01 — PRD First

The PRD is the official source of truth.

Never implement functionality that contradicts the PRD.

---

# Rule 02 — Respect the Sprint

Implement only the scope defined for the current sprint.

Never anticipate future features.

---

# Rule 03 — Keep It Simple

Always prefer the simplest solution that satisfies the requirements.

Avoid unnecessary complexity.

---

# Rule 04 — Reuse Components

Before creating a new component, verify whether an existing component can be reused.

Consistency is more important than variety.

---

# Rule 05 — Do Not Invent Requirements

If information is missing, do not make assumptions.

Use placeholders and wait for clarification.

---

# Rule 06 — Preserve the Architecture

Never modify the approved project structure without explicit authorization.

Folders, routes and organization must remain consistent.

---

# Rule 07 — Mobile First

Every interface must be designed considering mobile devices first.

Desktop adaptations come afterwards.

---

# Rule 08 — Responsive Design

Every page must work correctly on different screen sizes.

---

# Rule 09 — Clean Code

Write readable, organized and maintainable code.

Avoid duplication whenever possible.

---

# Rule 10 — Performance Awareness

Avoid unnecessary rendering, excessive complexity and oversized components.

---

# Rule 11 — Accessibility

Always use semantic HTML whenever possible.

Forms, buttons and navigation must follow accessibility best practices.

---

# Rule 12 — Naming Convention

Use clear and descriptive names.

Avoid abbreviations unless universally accepted.

---

# Rule 13 — Comments

Write comments only when they add value.

Prefer self-explanatory code.

---

# Rule 14 — Placeholder Policy

Whenever content is unavailable, use placeholders.

Never create fictional football information.

---

# Rule 15 — Future Features

If an idea belongs to a future sprint, do not implement it.

Register it as a suggestion instead.

---

# Rule 16 — Version Control

Every approved sprint must preserve compatibility with previous approved work.

---

# Rule 17 — Visual Consistency

Typography, spacing, colors and components must remain visually consistent throughout the platform.

---

# Rule 18 — Continuous Improvement

Suggestions are welcome.

Implementation only happens after approval.

---

# Final Principle

Build only what was requested.

Build it well.

Leave the project ready for the next sprint.
